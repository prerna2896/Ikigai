# Spec: AI Insights (Kenji's one-liner)

Status: **shipped and live-iterating.** This doc exists so the ongoing thread of small fixes/features on this surface doesn't get lost across sessions — update the checklists below as things land, rather than re-deriving state from scratch each time.

## What this is

A short, silence-by-default weekly observation from Kenji (the monk from onboarding) on `/insights`. Deterministic signal detection decides WHETHER anything is worth saying; the LLM's job is narrowed to phrasing an already-confirmed signal, never judging raw numbers itself. See `packages/insights/src/signals.ts` for the full rationale — this split exists because letting the LLM decide "should this fire" produced false positives.

## Architecture at a glance

```
app/insights/page.tsx (real page) ─┐
lib/prefetchWeeklyInsight.ts ──────┼─→ buildWeeklyMetricsSummary()  (packages/insights)
app/dev/insights-playground ───────┘         │
                                              ▼
                                   computeWeeklySignals()  — deterministic, unit-testable,
                                   zero LLM calls when nothing crosses threshold
                                              │
                                              ▼
                                   POST /api/insights/weekly  (zero DB access, stateless)
                                              │
                                              ▼
                                   buildInsightSystemPrompt() + buildInsightUserPrompt()
                                   → generateObject() → { shouldSpeak, insight, tone }
```

- **Signals** (`signals.ts`): `completion_drop`, `completion_improved`, `sustained_strong`, `allocation_drop`, `overachievement_tradeoff` (now multi-domain, see below), `sustained_underdelivery`, `overall_decline_ambiguous`. Each carries a `detail` string already phrased with the right noun (Ikigai principle name, not raw domain/task name — see "Naming" below) and an internal-only severity used for ranking; severity never crosses the network.
- **Selection** (`selectSignalsForInsight`, in `signals.ts`): decides which signal(s) the model even sees. Priority order: (1) `overall_decline_ambiguous` always wins alone if present — see "Week-shape classification" below; (2) two independent domain-scoped `attention` problems, found anywhere in the list, beat a solo anything else including a solo reallocation signal; (3) otherwise the single top-ranked signal, whatever it is. This is deterministic specifically because leaving "which signals to combine" to the model caused it to blend domain names across signals it was never told to pair (see Shipped log below).
- **Week-shape classification**: rather than only ever comparing individual domains, `computeWeeklySignals` first asks a totals-level question — did overall logged hours fall off a cliff (`overall_decline_ambiguous`, cause deliberately left unguessed — see below), are they flat but redistributed across domains (`overachievement_tradeoff`, now naming up to 2 domains that eased off, not just one), or is nothing exceptional happening (silence, or existing per-domain `sustained_strong`)? This mirrors three scenarios explicitly named by the user: an ambiguous overall decline (life event vs. logging-habit change — genuinely can't be told apart from hours data, so the insight states the fact and a separate UI prompt asks directly, reusing the completion-drop context-prompt mechanism), a stable-total reallocation (hours moved between domains), and steady-state (already covered, no new signal needed).
- **Detailed trend view** (`app/insights/page.tsx`): a collapsible "Task trend by domain" section below the one-line insight, showing each domain's planned-vs-logged completion across the same weeks already fetched for the chronic-signal check (no new data fetching) — lets someone inspect the numbers behind whichever scenario fired instead of only getting the one-sentence summary.
- **Prompt** (`prompt.ts`): Kenji's voice, tone rules per coaching style (`coachingStyles.ts`), and three research-backed language patterns (NVC observation-not-evaluation, MI-style affirmation, autonomy-supportive phrasing).
- **Personality** (`traits.ts`, `coachingStyles.ts`, `personas.ts`): derived once from onboarding reflection answers, drives tone only — not currently informed by ongoing weekly reflections (see Open questions).
- **Feedback loops**: real-user reactions → `insight_reactions` Supabase table (`/api/insights/reaction`, write-only). Playground reactions + freeform notes → local `.data/insights-playground-feedback.jsonl` (git-ignored), explicitly kept separate from the real table. Read this file when tuning the prompt — it's the actual, first-party record of what's read as robotic/wrong.

### Playground feedback is a manual-review log, not a live loop

Worth stating plainly since it caused real confusion: reactions/notes left in `/dev/insights-playground` save correctly to `.data/insights-playground-feedback.jsonl`, but nothing reads that file automatically — there's no live retraining or self-editing prompt. It exists so *I* (whoever's working on this next, across sessions) can read it and manually turn it into prompt edits, same as every fix in this log. Leaving feedback and re-running the same fixture will reliably produce the same output until someone reads the file and changes `prompt.ts` by hand.

First version allowed an optional model-composed closing clause with detailed safety criteria (win-domain-only, no command, no causation, no goal) — live batch testing (30 generations) found 0 rule violations but also found the model reusing the general "it'll be there whenever you circle back to it" reassurance verbatim, aimed at the WRONG (pull-back) domain, 1/15 times. Verified via 30 more batch generations across two scenarios (one dropped domain + a goal set; two dropped domains, no goal): 0/30 violations, closing clause appearing naturally at roughly the target rate, e.g. "Contribution's come in well ahead of plan, while Energy has stepped back — and it shows."
